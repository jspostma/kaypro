Kaypro ROM — Code Explainer

This guide walks through the ROM source code for the Kaypro 2/4 (specifically the 81-292 family, the ROM in your Kaypro 4), explaining what each part does and why. It's written for someone comfortable with Python and Arduino-level C, with minimal assembly experience.

The primary source used is kaypro/software/roms/boot/81-292/kp81_292.mac — a 2006 reverse-engineering of the 81-292 EPROM. Where the raw disassembly is hard to follow, we cross-reference k10rom7a/ROM7A.MAC (the Kaypro 10 ROM with developer comments) and the CP/M 2.0 Alteration Guide. Differences specific to the 292-A are called out with 292-A tags.

CP/M Architecture

CP/M is structured as three layers. The ROM implements the bottom layer:

Arduino analogy
Think of it like the Arduino library ecosystem: CCP = your sketch (user-facing), BDOS = the Arduino standard library (file I/O abstraction), BIOS = the low-level HAL that talks directly to hardware. The ROM contains the BIOS plus the boot loader that loads CCP+BDOS from disk.
LayerNameWhat it doesWhere it lives
TopCCP — Console Command ProcessorThe shell. Parses commands like DIR, TYPE, runs programs.Loaded from disk into RAM (~0xE400)
MiddleBDOS — Basic Disk Operating SystemFile system. Programs call BDOS to open files, read sectors, etc. It's hardware-independent.Loaded from disk into RAM (~0xEC06)
BottomBIOS — Basic I/O SystemHardware drivers. BDOS calls BIOS for disk, keyboard, serial, video. Hardware-specific — this is what the ROM provides.Loaded from disk sector 0 into RAM (~0xFA00), or provided by ROM on first boot.
—Cold-start loader (in ROM)Reads the OS (CCP+BDOS+BIOS) from track 0 of the disk and copies it to RAM.In the 8KB EPROM at address 0x0000

The ROM (EPROM, part 81-292 or 81-292-A) handles everything until CP/M is running. After that, the ROM is no longer directly called — control stays in RAM. The BIOS jump table in RAM is what CP/M actually uses.

Memory Map

The Z80 has a 16-bit address bus = 64 KB of address space. Here's how it's used in two different moments:

While CP/M is running (ROM switched out)

CCP~0xE400
BDOS~0xEC06

The ROM bank switch

On power-up, the ROM appears at 0x0000 because the Z80 always starts executing at address 0. But CP/M needs address 0 to be RAM (it stores jump vectors there). The Kaypro solves this by having the ROM copy the BIOS to RAM, then "switch itself out" — a control bit in the hardware makes RAM appear at 0x0000 instead of the ROM. After that point, the ROM chip is invisible to the CPU.

Analogy
It's like an Arduino sketch that bootstraps a second, more capable sketch from an SD card and then hands over control. The ROM's only real job is "load CP/M from disk and get out of the way."

Scratch RAM variables

The ROM uses a block of fixed RAM addresses at the top of memory to store its working variables — things like "which disk is selected," "what's the current cursor position," "which baud rate are we running." In the 292 ROM, this area starts around 0xFB00 and another chunk at 0xFD00. These must survive across calls (the ROM has no stack-allocated globals like a C program would). Think of them as the Z80 ROM's equivalent of global variables.

The Jump Table — the BIOS API

Right at address 0x0000, before the reset vector, the ROM contains a jump table: a list of JP instructions. Each JP is 3 bytes (opcode + 16-bit target address), so the table entries are at fixed, well-known addresses.

C++ / Python analogy
The jump table is exactly like a vtable (C++ virtual methods) or a dict of function pointers. CP/M's BDOS doesn't know (or care) what hardware it's running on — it just calls a fixed address like CALL 0x0012 and the ROM routes that to the correct driver. In Python terms: it's a dispatch table, bios = {"seldsk": fn_seldsk, "read": fn_read, ...}.

The 292 ROM jump table at address 0x0000 (each JP is 3 bytes → entries at 0, 3, 6, 9, ...):

Notice that this jump table is in ROM at power-on, but after CP/M loads, it builds a new jump table in RAM at 0x0000 that points to the BIOS routines it loaded from disk. The ROM table is only used during the boot process itself.

Boot Sequence — Step by Step

The Z80 resets to address 0x0000. Execution begins at the first instruction after the jump table (at address 0x004B in the 292 ROM):

; cold start entry point — arrives here from JP at 0x0000
BOOT:
    DI                  ; Disable interrupts — we're not using them yet
    LD   SP,0FFFFh      ; Set stack pointer to top of RAM (grows down)
    LD   B,0Ah           ; Delay count
    CALL 579h            ; delay() — wait for power to stabilise
    CALL 13Ch            ; devinit() — init serial ports
    CALL 6DAh            ; vidinit() — init video, clear screen
    CALL 244h            ; diskinit() — init floppy controller
    JR   67h             ; jump forward to boot loader proper
Arduino analogy
This is exactly Arduino's setup(): disable interrupts, set up the stack, wait for power rails to settle, then call init functions for each peripheral in order.

Step 1: Power-on delay

The very first thing is a software delay. This gives capacitors time to charge and voltage rails to stabilise — common on old hardware where there's no power-good signal. The delay routine (0x0579) is a simple nested countdown loop: B×686×256 iterations of DJNZ.

Step 2: devinit — serial port setup

Initialises the Z80 SIO chip and the 8253 baud rate generator. See the Device Init section.

Step 3: vidinit — video setup

Configures the 6545 CRTC chip and clears the screen. See the Video section.

Step 4: diskinit — floppy controller setup

Resets the WD179x FDC. See the Disk I/O section.

Step 5: Load the OS from disk

The loader displays the prompt, then reads from track 0 of drive A:

; Boot loader — show prompt, try to load OS
    CALL 0A80h          ; print_string() — output null-terminated string that follows
    DB   ESC,"=*?*     KAYPRO      *",ESC,"=-4"
    DB   " Please place your diskette into Drive A",BS,0
; SETDMA(0xFA00) — load sectors to 0xFA00 (BIOS entry point)
    LD   BC,0FA00h
    CALL 285h            ; SETDMA
    CALL 2AAh            ; READ sector 0 track 0
    DI
    OR   A
    JR   NZ,10Ah        ; if read failed → error "I cannot read your diskette"

The boot sector format

Sector 0 of track 0 on a Kaypro CP/M disk has a specific structure (documented in k10rom7a/ROM7A.MAC):

OffsetContentNotes
+0Jump-over header codeJR $ (hang if executed raw)
+2Load address (word)Where in RAM to put the OS — typically 0xE400 (CCP start)
+4BIOS entry address (word)The address of the BIOS cold-start entry in the loaded image
+6Length in 128-byte sectors (word)How many more sectors to read

The loader reads this header, then loops reading sectors from track 0 (and overflowing to higher tracks) until it has loaded the entire CCP+BDOS+BIOS image into RAM. Then it jumps to the BIOS cold-start entry to hand off control.

Step 6: Error handling

If any sector read fails, the loader prints:

"\r\n\n\a"
"I cannot read your diskette."

Then it calls diskoff, and loops back to the prompt. The user must remove and replace the disk, or the machine loops forever.

Device Init — Serial Ports (devinit, 0x013C)

The Kaypro 4 has three serial "channels":

  • Channel A (console): the keyboard (input) and video output path — but video goes through its own logic, keyboard is the UART side of channel A.
  • Channel B (modem/serial): the RS-232 port on the back of the machine.
  • Parallel port: for the printer.

The Z80 SIO chip

The Z80 SIO (Serial I/O) is Zilog's own UART chip. It has two channels (A and B) each with data and command registers. You configure it by writing to "Write Registers" (WR0–WR7) and read status from "Read Registers" (RR0, RR1, RR2).

Arduino analogy
Writing to the SIO is like calling Serial.begin(9600) in setup() — you're telling the hardware "I want 8N1, at this baud rate, receive ready interrupt off." But instead of a friendly API, you write raw bytes to I/O ports.

SIO port assignments (292 ROM)

PortChannelDirection
0x00 (0)SIO Channel A — DataRead keyboard / write to channel A
0x01 (1)SIO Channel B — DataRead/write modem/serial port
0x02 (2)SIO Channel A — ControlWrite config commands, read status
0x03 (3)SIO Channel B — ControlWrite config commands, read status
0x04–0x078253 PIT (timer/baud rate gen)Sets baud rate divisors

SIO initialisation sequence

The devinit routine (at 0x013C) sends a series of bytes to port 0x14 (the parallel port latch) and to the SIO control port to configure both channels. The raw bytes in the ROM are:

; Parallel port / control latch setup
    LD   A,0DFh
    OUT  (14h),A

; SIO reset sequence — always start by writing WR0 = reset
    LD   C,7             ; channel to initialise (port offset)
    CALL 147h            ; write_sio_reg(C, config_table)
    LD   C,0Eh
    LD   HL,133h         ; pointer to init bytes table
    LD   B,9             ; 9 bytes to send
    OTIR                ; output B bytes from (HL) to port C, B=0 when done

OTIR is a Z80 block instruction: "Output bytes from memory to I/O port, incrementing HL, decrementing B until B=0." In Python: for byte in config_table: port_write(C, byte).

The init byte table at 0x133 contains the values for SIO Write Registers (WR0–WR4 for each channel), configuring 8 data bits, no parity, 1 stop bit — the classic "8N1" serial setup.

Baud rate

The 8253 Programmable Interval Timer runs as a baud rate clock. The ROM writes a divisor to the 8253 to set the baud rate. The Kaypro stores the current baud rate setting in scratch RAM (at 0xFD17h in the 292 ROM), and the SIO can be reconfigured at runtime via escape sequences or the TERMINAL command on replacement ROMs.

Video — vidinit and vidout

The hardware

The Kaypro 4 screen is 80×24 characters (80 columns, 24 rows = 1920 character cells). The display hardware is:

  • 6545 CRTC (Cathode Ray Tube Controller) — a dedicated chip that generates the video timing signals and manages the video RAM address. You program it by writing pairs of (register number, value) to two I/O ports.
  • Video RAM — a dedicated block of RAM that the CRTC reads to determine what character is at each position. On the Kaypro it's mapped into the CPU address space at a specific area (the 292 ROM stores its address in scratch var 0xFD7Ah).
  • Character ROM — a separate EPROM (81-146a, the 2KB one in your archive) that maps character codes to pixel bitmaps. The CRTC uses this to draw each character row-by-row during horizontal scan.

vidinit (0x06DA)

Sends the CRTC configuration registers to set up screen geometry and initialises the video RAM pointer in scratch RAM:

; CRTC init table at 0x76D — 16 values for registers R0..R15
crtc_init:
    DB   6Ah  ; R0:  horizontal total (106 chars)
    DB   50h  ; R1:  horizontal displayed (80 chars)
    DB   56h  ; R2:  horizontal sync position
    DB   99h  ; R3:  horizontal/vertical sync widths
    DB   19h  ; R4:  vertical total (25 rows)
    DB   0Ah  ; R5:  vertical adjust
    DB   19h  ; R6:  vertical displayed (24 rows + 1 status)
    DB   19h  ; R7:  vertical sync position
    DB   78h  ; R8:  interlace and delay
    DB   0Fh  ; R9:  max scan line (16 scan lines/char)
    DB   60h  ; R10: cursor start line + blink mode
    DB   0Fh  ; R11: cursor end line
    DB   00h  ; R12: start address high (video RAM at 0x0000 relative)
    DB   00h  ; R13: start address low
    DB   00h  ; R14: cursor address high
    DB   00h  ; R15: cursor address low

The CRTC talks via ports 0x1C (register select) and 0x1D (data). Writing a register is always a two-step: first write the register number to 0x1C, then write the value to 0x1D.

Arduino analogy
This is like configuring an SPI or I2C peripheral: write an address/register byte, then write the data byte. Wire.write(reg); Wire.write(value);

vidout (0x077D) — the character output routine

This is the most complex routine in the ROM. It receives a character in register C and decides what to do with it. There are three cases:

  1. Printable character (0x20–0x7F): Write it directly to the video RAM at the current cursor position, advance the cursor. If the cursor reaches the end of the line, wrap to the next line. If it's at the last row, scroll the screen up.
  2. Control character (0x00–0x1F): Handle as a special action — newline, carriage return, backspace, bell, etc.
  3. ESC sequences (0x1B followed by more bytes): A state machine. After seeing ESC, the next byte(s) select a command. Kaypro uses ADM-3A terminal codes plus some extensions.

ESC sequence state machine

The video state is stored in scratch RAM variable 0xFD74h. When 0, normal operation. When non-zero, we're mid-sequence. The ROM implements a complete terminal emulator:

ESC sequenceAction
ESC = row colMove cursor to position (row-32, col-32) — direct cursor positioning
ESC ACursor up
ESC BCursor down
ESC CCursor right
ESC DCursor left
ESC EErase screen, home cursor
ESC YErase to end of line
ESC jReverse video on
ESC kReverse video off
ESC pEnter graphics mode
ESC G 0–7Set video attribute bits
ESC H 0–7Clear video attribute bits

How video RAM works

The 6545 CRTC treats video RAM as a flat array of character codes. At 80 columns × 24 rows, that's 1920 bytes. The CRTC has a start address register (R12/R13) that tells it where in RAM the top-left of the screen starts. The ROM uses this to implement hardware scrolling: instead of copying 1920 bytes up one row (slow), it just increments the start address by 80 bytes, pointing the CRTC at the second row — effectively moving the "window" forward through a circular video RAM buffer. The buffer size is 2048 bytes (0x800), giving a small amount of "off-screen" wrap-around space.

Analogy
Hardware scrolling via the CRTC start address is like changing where array[0] starts in a ring buffer — you don't move the data, you move the pointer. The visual result is instant scroll with zero CPU effort.

Disk I/O

The WD179x FDC

The Kaypro uses a Western Digital FD179x (also known as FD1793 or WD1793) Floppy Disk Controller chip. This chip handles all the low-level floppy stuff: head stepping, reading/writing magnetic flux reversals, CRC checking, sector ID detection. You don't interact with the disk at bit level — you tell the FDC "read sector N from track T on side S" and it does the physical work.

Analogy
The FDC is like an SD card module with a simple command interface: you set up parameters, send a command, wait for the interrupt/status flag, then read the data. Much simpler than bit-banging SPI at the magnetic level yourself.

diskinit (0x0244) — FDC reset

Sends a "Force Interrupt" command (0xD0) to the FDC to reset its state, then reconfigures the control latch. It also copies a small routine to scratch RAM at 0xFDE5 (the actual sector read/write inner loop — see the "relocate to FDE5H" comment in the source). This is done because the read loop runs during a DMA-like "read data byte by byte as they come off disk" phase that needs to be as fast as possible, and upper RAM is closer to no wait states.

HOME (0x0296) — seek to track 0

; Send RESTORE command to FDC — seeks head to track 0
    LD   A,0D0h          ; Force interrupt (abort any in-progress command)
    OUT  (10h),A
    CALL 563h            ; diskon() — motor on, select drive
    LD   A,0
    OUT  (10h),A          ; Command 0x00 = RESTORE (step in until track 0)

SELDSK (0x0272) — select disk drive

Called with C = drive number (0=A, 1=B). Must return HL pointing to the Disk Parameter Header (DPH) for this drive, or HL=0 if the drive number is invalid.

SELDSK:
    LD   A,C
    LD   (0FB00h),A    ; save disk number to scratch RAM
    JP   3DBh           ; → compute DPH address and return in HL

SETTRK / SETSEC / SETDMA

These three routines just store their argument into scratch RAM variables. Nothing happens to hardware yet — they're just "loading parameters for the next READ or WRITE."

SETTRK:  LD A,C  LD (0FB03h),A  RET   ; save track to 0xFB03
SETSEC:  LD A,C  LD (0FB00h),A  RET   ; save sector to 0xFB00
SETDMA:  LD (0FB14h),BC  RET           ; save DMA address (BC) to 0xFB14

READ (0x02AA) — the actual disk read

READ is the most complex disk routine. It:

  1. Checks if we need to step the head to a new track (if different from the currently seeked track, issues a SEEK command to the FDC)
  2. Handles side selection (double-sided disks: track 0–39 on side 0, track 40–79 on side 1)
  3. Sends the READ SECTOR command to the FDC (command byte 0x88)
  4. Reads 128 bytes from the FDC data port (0x13) one byte at a time, using INI / HALT
  5. Returns 0x00 in A on success, non-zero on error

The HALT trick — waiting for byte-ready

The inner read loop in the 292 ROM uses HALT to wait for each byte:

LD   A,88h           ; READ SECTOR command
OUT  (10h),A
rd_loop:
HALT                ; CPU halts here until /INT is asserted
INI                 ; Read byte from port (HL) to RAM at (DE), decrement BC
JR   NZ,rd_loop     ; Loop until BC=0 (128 bytes read)
What HALT is doing here
The FDC asserts /INT (interrupt line) when each byte is ready to be read. With DI (interrupts disabled), HALT makes the CPU pause execution until /INT is asserted — then resumes at the next instruction (not an ISR, because interrupts are disabled). It's essentially a hardware-assisted busy-wait: "pause until the FDC says it has a byte." This is faster and more reliable than polling the status register in a loop.

WRITE (0x02C5)

Mirror of READ: seek if needed, send WRITE SECTOR command (0xA8), then use HALT + OUTI to send 128 bytes to the FDC data port one byte at a time.

Retry logic

Both READ and WRITE have retry logic. The outer loop (in the routines around 0x0590) retries up to 16 times. On retry, the ROM performs a HOME (seek to track 0) and tries again — a common recovery strategy for floppy errors caused by head misalignment. If all retries fail, returns error code 0xFF.

Disk Parameter Tables

CP/M's BDOS doesn't know the physical geometry of the disk. It sees abstract "tracks" and "sectors." The BIOS provides a set of data tables that describe the disk geometry to BDOS. These are the Disk Parameter Block (DPB) and Disk Parameter Header (DPH).

Analogy
Like a filesystem superblock: the DPB tells BDOS "this disk has 77 tracks, 26 sectors/track, sectors are 128 bytes, there are 64 directory entries, 2 reserved tracks for the OS..." BDOS can then allocate blocks and find files generically.

The 292 ROM has tables for two drive geometries. The second DPB (for drive B or double-sided) has different parameters: 40 sectors/track, 194 DSM, 63 DRM, OFF=1.

Sector skew / SECTRAN (0x0536)

Physical sectors on a floppy aren't read in order 1, 2, 3, 4... Instead, they're interleaved. The Kaypro uses a skew of 2 — sector 1 physically follows sector 4, etc. This is because the head moves faster than the disk can deliver data: if you read sector 1, then immediately seek to sector 2, the disk has already rotated past sector 2 and you have to wait a full revolution. By skewing, you put logically sequential sectors physically far apart, so you have time to seek between them. The SECTRAN routine maps a logical sector number to a physical one using a lookup table embedded in the ROM.

The skew table for the 292 ROM (logical → physical):

; Drive A skew table (18 sectors, interleave 2)
DB 1,6,11,16,3,8,13,18,5,10,15,2,7,12,17,4,9,14

Keyboard

On the Kaypro, the keyboard is connected to SIO Channel A (the same SIO chip as the serial port, but channel A). The 8048 microcontroller inside the keyboard scans the key matrix and sends serial bytes down the line to the Z80 SIO. The keyboard controller sends raw keycodes, not ASCII — the ROM translates them.

kbdstat (0x014F) — is a key pressed?

kbdstat:
    IN   A,(7)            ; Read SIO channel A status (port 7 = RR0 channel A)
    AND  1               ; Check bit 0 = Rx Character Available
    LD   A,0             ; A = 0 (no key)
    RET  Z              ; return 0 if no key waiting
    LD   A,0FFh          ; A = 0xFF (key ready) — CP/M CONST convention
    RET

kbdin (0x0159) — read a key

kbdin:
    CALL 14Fh            ; kbdstat() — wait for key
    JR   Z,159h          ; loop if no key yet
    IN   A,(5)            ; Read byte from SIO channel A data (port 5)
    CALL 16Eh            ; translate() — decode keycode to ASCII
    RET

Key translation

The translate routine at 0x16E searches a lookup table embedded in the ROM (at 0x183). It receives a raw keycode from the keyboard controller, searches the table for it, and returns the corresponding ASCII character. The table has two parts:

  • DB 0xF1, 0xF2, 0xF3... — raw keycodes for the function/special keys
  • DB 0x80, 0x81, 0x82... — corresponding translated values (extended ASCII or control chars)

Normal alphanumeric keys come through directly as ASCII from the keyboard 8048 controller (the 8048 does the basic scan-to-ASCII mapping).

Scratch RAM — the ROM's Global Variables

The ROM has no BSS segment or heap — it's in a ROM. All state that persists between calls is stored in fixed RAM locations at the top of the address space. The CP/M BIOS that loads from disk uses a similar scratch area.

292-A vs K10 (v7A) — What's Different

Your Kaypro 4 has an 81-292-A ROM. The best-documented Kaypro ROM source in the archive is the Kaypro 10 v7A (k10rom7a/) with developer comments. Here's what's different:

1. Hard disk support

292-A: No hard disk
The K10 ROM has an entire module (HDIO7A.MAC, 16 KB) for Winchester hard disk support — the Kaypro 10 had a 10 MB hard drive. The 292/292-A only supports two floppy drives. The disk init, read, write, and parameter tables are floppy-only. If you look at the K10 source, you'll see a dsktyp variable (in RAM.MAC) that switches between floppy and hard disk code paths. The 292 ROM has no such switch.

2. Drive B overlay mechanism

K10 only: loads an overlay from drive B
The K10 boot ROM loads a 2KB overlay from track 0 sectors 0–15 of drive B into RAM at 0xEE00 after booting. This overlay patches the BIOS (adds printer support, etc.) and is specific to the K10 configuration. The 292 ROM doesn't do this — it loads everything it needs from drive A sector 0 directly.

3. CRTC timing values

292-A: Different CRTC init
The 292 ROM's CRTC init table (at 0x76D) has slightly different values from the K10. The K10 CRTC init uses 0x78, 0x50, 0x58, 0x0A, 0x1F, 0x06, 0x19, 0x1C, 0xC8, 0x07, 0x60, 0x07. The 292 uses 0x6A, 0x50, 0x56, 0x99, 0x19, 0x0A, 0x19, 0x19, 0x78, 0x0F, 0x60, 0x0F. R9 (max scan line) is 0x07 on K10 (8 scan lines/char) vs 0x0F on 292 (16 scan lines/char), reflecting different display hardware in the two models.

5. Disk parameter tables

292-A: Single-sided and double-sided 5.25" floppies only
The 292 ROM has two DPBs: one for single-sided (1S/2D) and one for double-sided drives. The K10 has three DPBs: single-sided 5.25", double-sided 5.25", and 8" floppy. If you're using a double-sided drive on your Kaypro 4, the ROM detects it by trying to read from side 1 and sets flag 0xFD18=0x20 for double-sided mode.

6. Source quality

Note on the available 292 source
The file kp81_292.mac is a reverse-engineered disassembly from 2006, not original source. It has no symbolic labels for most jump targets — they all appear as raw hex addresses (e.g. JP 272H instead of JP seldsk). The K10 source (k10rom7a/) is the actual developer source with comments, and is the best reference for understanding intent. The two ROMs are structurally very similar — the same engineer(s) wrote them — so the K10 comments generally apply to the 292 too.

7. The 292-A suffix

A vs non-A
The disassembly in the archive is of the 81-292 (no letter suffix). The 81-292-A (your ROM) is a minor revision. Based on the version matrix, both are CP/M 2.2F, so the changes are likely small bugfixes. Without a dump of the 81-292-A specifically, we can't say exactly what changed. The KP-CBOOT.DOC file in the archive documents specific memory addresses in "the K10 CP/M 2.2F ROM" which should be applicable to the 292-A as well.

Note on the ROM bank switch
Bit 6 of the control latch is how the ROM switches itself out after loading CP/M. Once CP/M's BIOS cold-start routine runs, it writes to port 0x14 with bit 6 set, which causes the hardware to map RAM instead of ROM at 0x0000. After this point the CPU can never see the ROM again until the next power cycle or reset.
